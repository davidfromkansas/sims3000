The integrated source milestone now includes form authoring, scheduling, execution, messages/history, city saves, named saves, worker execution and replay. ## Manual evidence and intended player functionality

The supplied manual, printed pp.188–189 (local extracted text lines6653–6684 and6718), specifies If, If Else, multi-instruction condition/action blocks, Subroutine and Repeat Regular. Existing scheduled events can watch a condition and execute one action; grouped events are not equivalent to an If/Else block. The intended milestone lets authors create ordered action sequences with branches, call named reusable routines and schedule repeated entry calls. Players can encounter different messages, goal updates, rewards and disasters based on the city's current state.

Do not replace this with merely another condition operator or four independent event rows. Preserve all existing scenario files and event timing behavior.

## Execution foundation now implemented

`dist/scenario-programs.js` compiles structured action / if / call nodes into an internal instruction sequence. Conditions and actions use injected game validators; there is no source-code evaluation. Branches read city state when reached. A chosen branch stays chosen across pauses, while a later If reads the then-current state. Subroutine calls use a persistent return stack. Emitting an action advances the cursor before the host pauses, so a saved popup cannot repeat the emitted action when resumed.

Bounds are explicit reconstruction/runtime choices: eight named routines, eight block nesting levels,128 source nodes across routines, and a conservative1024 expanded instruction maximum per entry invocation. Calls must target an existing routine. Recursive call graphs and exponentially expanded routines are rejected before gameplay. Empty routines and missing Else blocks are legal no-ops. Internal compiled code must be rebuilt from validated source, never trusted from imported saves.

`tests/scenario-programs-core.test.mjs` passes with real event/condition validators and a real city: true/false arms, action order, nested routine returns, popup cursor JSON roundtrip, branch stability after population changes, recursion/expansion rejection and invalid return addresses. It is deliberately not yet included in the release test command: integration will add it with the full milestone. This test proves interpreter behavior, not live popup delivery, actual rewards/disaster execution, city save compatibility or editor usability.

## Shared game action checkpoint

`executeScenarioAction(c, action, index)` now lives in `scenario-events.js`. Existing scheduled events call it, then store their existing progress/runs shape. It preserves primitive effects, captured text, popup acknowledgement flags, deterministic arithmetic seed index, division failure results, offers and nearest-target disaster selection. Unknown action types throw instead of falling through to a locust attack. The executor intentionally does not schedule, acknowledge, or end the scenario by itself; hosts must record and present its result.

## Persistent invocation checkpoint

`scenario-program-history.js` now supplies a game-facing invocation runner and strict history validator. An invocation contains its entry cursor, boolean branch choices, compact action receipts, the latest32 captured messages and an ending flag. The supported invocation id range0–47 corresponds to the existing maximum four event rows × twelve occurrences; the schedule integration must bind ids to those rows/occurrences, not trust arbitrary imported ids.

The runner emits one actual action at a time through `executeScenarioAction`, records its result with the post-action instruction step, and advances only while the scenario is playing, no emergency is active and no popup is pending. A popup waits for explicit acknowledgement. An ending stops the routine before later actions. The eventual host still must present the popup/disaster and finish the scenario; no such integration is claimed yet.

The validator reconstructs control flow from recorded branch choices, proves that every receipt matches an action reached by that flow, validates results with the existing event-progress rules, and checks the final cursor against the reconstructed stack. It does not rerun old city mutations or reevaluate conditions against today's city. Action receipts remain after old message text is evicted, retaining goal-change provenance. Message history must be exactly the most recent32 text actions; pending messages cannot be skipped or evicted by further execution.

`programActionSources` projects validated receipts into shared goal-history sources. `validateGoalMarks` and `validateGoalActivations` accept an optional final programSources argument; existing callers retain identical behavior. Program activation evidence requires the exact recorded action month, while legacy repeated-event evidence retains its established range semantics. Only validated/live-produced invocation records may be passed to this projection. City save validation has NOT yet been wired to supply these sources.

## Invocation binding and popup integration checkpoint

`scenario-program-invocations.js` validates an invocation collection against routine-entry event definitions and their progress rows. It binds `id = eventIndex * 12 + zeroBasedOccurrence`, checks the compiled entry routine, requires contiguous occurrences, and rejects duplicate/missing invocation records, overlaps, execution after an ending and starts before the scheduled/repeat date. It returns only validated invocations and their action-source projection. This boundary currently assumes its caller has validated event definitions; the normal custom-definition/event loaders do not yet accept routine entries.

Invocations now record `finishedMonth` (null until complete/ended). Event runs count started occurrences. Their progress month is the latest invocation's start while active, then its finish when complete. Repeats wait the configured interval after completion, following the existing completion-relative event policy when an occurrence is delayed. Active invocations must separately block required-event victory. These semantics must be stated in the editor; they are authored reconstruction choices, not the original interpreter's recovered timing.

The actual `pendingScenarioPopup` API now falls back to `pendingProgramPopup` after legacy scheduled messages. The existing message dialog reads bounded program text while acknowledging the original receipt in-place, preserving its normal save and close behavior. No program can reach this path from a normally loaded city yet; complete schedule/definition/state integration is still required.

`tests/scenario-program-invocations.test.mjs` passes with two interleaved scheduled entries, a delayed acknowledged popup, completion-based repetition, strict occurrence binding, missing/duplicate/early-history rejection and an actual `showPendingScenarioPopup` handler test proving one save when both the button and close event acknowledge the same message. The existing popup regression and all three earlier program suites also pass. No schema/graph change, commit, PR or deployment.
